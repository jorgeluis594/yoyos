# Products

A product is something a company sells. Products are managed from the core web app (`/products`) and from the mobile app (**Productos** tab). Core is the source of truth for validation, identifiers, prices, stock, images and persistence; mobile adapts navigation and controls but follows the same rules through `/api/products`.

Code: `apps/core/src/features/products/` (core), `apps/mobile/src/features/products/` (mobile). JSON contracts: `shared/contracts/products.ts`. Editor rules shared by web and mobile: `shared/product-variants.ts`. Schema: `Product`, `ProductOption`, `ProductOptionValue`, `ProductVariant`, `ProductVariantOptionValue` and `ProductStock` in `apps/core/prisma/schema.prisma`.

## Model

- A product has a name, an optional description, an optional photo (one `imageId`, see [Images](images.md)), a currency, up to 3 ordered options and at least one variant.
- An option has a name and an ordered list of values («Talla»: S, M, L). A variant is one value of each option; its **combination** is written in option order and separated by « / » («L / Azul»). A product without options has exactly one variant with an empty combination.
- A variant has an optional SKU, a sale price, an optional purchase price, exactly one stock record, a status (`active` or `inactive`) and an immutable QR identifier. The QR is separate from the internal id and the SKU; it is what labels print and what [message-to-order](message-to-order.md) reads from photos.
- The product also has an immutable QR identifier and a structure version that increases on every structural write (see [Concurrency](#concurrency)).
- Options, values and variants keep the order the seller gave them. That order is used by the product screens, the variants table, the combination label, the print sheet and label, «Nueva venta», the [public catalog](public-catalog.md), the [checkout](checkout.md) and new [orders](orders.md). Reason: S, M, L is not alphabetical.
- There is no product deletion, archiving or category. A product with options stops being sold by deactivating all its variants; a product without options cannot be withdrawn.

## Rules

| Aspect | Rule |
| --- | --- |
| Access | Any authenticated user of the company can create, view and edit its products. The company comes from the session, never from the request. A product or variant of another company behaves as non-existent. |
| Name | Required, up to 200 characters. Duplicate names are allowed. |
| Description | Optional, up to 5,000 characters. |
| Limits | 3 options per product, 30 values per option, 100 variants per product, and 1–30 characters per option or value name after trimming. They are constants of the shared contract so the editors apply them without a round trip; core validates them again. |
| Option and value names | Required. Two options, or two values of one option, cannot match ignoring case and surrounding spaces. |
| Combination | A variant has exactly one value of each option. Two variants of a product, active or inactive, cannot have the same combination. Not every combination must exist: the seller removes the ones she does not sell. |
| SKU | Optional, up to 100 characters, never generated or copied between variants. Unique per company ignoring case and surrounding spaces (database constraint); many variants may have none. |
| Prices | Per variant. Sale price greater than zero; purchase price optional and zero or more. Two decimals at most, maximum 999,999,999.99 in the product currency. Excess precision is rejected, never rounded. |
| Currency | The client sends the currency explicitly, taken from the company's country (PE→PEN, US→USD, CO→COP, AR→ARS, CL→CLP, BR→BRL). Core validates the code. It cannot be edited. Reason: the contract allows a currency selector later without changing the API. |
| Stock | Per variant. The initial stock (zero or more, default zero) is set only when the variant is created. Afterwards users cannot edit it; it changes only when an order deducts it and when a cancelled order that had deducted it restores it. The product shows the sum of its active variants, read-only. |
| QR | One per variant, generated by core when saved and never changed by renaming, reordering, changing the combination, deactivating or reactivating. |
| Renaming | Renaming an option or value renames it in all its variants. Orders and checkouts already created keep the text they copied; printed labels keep the old name and their QR keeps working. |
| Values without variants | Every save (editor, change combination, delete variant) drops from the option any value left with no variant, counting inactive ones, and then any option left with no values. The value is dropped, not rejected. |
| Adding a value | Creates only the combinations that contain it, with the price of the first existing variant that shares the other values (preferring an active one), stock 0 and no SKU. A value created while changing one variant's combination creates no other combination. |
| Adding an option | Existing variants, active or inactive, receive the value the seller chose and keep their id, QR, SKU, prices, stock, status and orders. The other combinations are created as new variants. A product without options may receive its first option the same way. |
| New variants | Always created active, even when copied from an inactive one. |
| Changing a combination | Allowed even if the variant has orders or is inactive, as long as it does not repeat another variant's combination. Orders keep their copy. It is saved at once. |
| Deleting a variant | Only if it never appeared in any order (unconfirmed catalog orders count), its stock is 0 and it is not the product's only variant. Otherwise it is deactivated, never deleted. The variant, its QR and its zero stock are removed. |
| Deleting a value | Deletes all its variants, so each one must meet the deletion conditions. Core checks it again on save. |
| Deleting an option | Only an option with a single value; the variants lose that attribute and keep everything else. If it was the last option the remaining variant must be active and the product becomes a product without options. |
| Deactivating | Only for products with options, including the last active variant. An inactive variant leaves the public catalog, «Nueva venta», QR and photo lookups of message-to-order, and the «Desde» price and total stock of the list. It keeps its QR, SKU, prices, stock and orders; with stock above zero the seller is warned, not blocked. **Activar variante** returns it with its stock. |
| Orders with an inactive variant | Orders that already contain it keep working: they are shown, paid (stock is deducted) and cancelled (stock is restored), including an unconfirmed catalog order the buyer reopens with **Continuar**. No new order can be created with it from web, mobile, the catalog or message-to-order; the item is marked «ya no está disponible». |
| Product without active variants | Not offered by the catalog or «Nueva venta» and not recognized by message-to-order. It stays in the list marked «Sin variantes activas» and returns to sale when any variant is activated or added. |
| Data copied into orders | The product name, the combination (names and values in option order at that moment), the SKU and the price. Later edits, renames, reorders, deactivations or deletions never change an order or a checkout. |
| Concurrency | See [Concurrency](#concurrency). |

## Screens

Web and mobile apply the same rules, limits and error codes. Mobile creates and edits on full screens without the tab bar.

- **List:** newest first; name, SKU («Varias variantes» when there are several, «Sin SKU» when absent), sale price («Desde» the minimum of the active variants when prices differ) and total stock of the active variants. A product without active variants shows «Sin variantes activas» instead of the price. Search is partial and case-insensitive over the product name and any variant SKU; each product appears once. Pages of 20 (web numbered pages, mobile **Cargar más**). An empty catalog, a search without results and a load failure are distinct states.
- **Create:** name, description, photo, SKU, sale price, purchase price and initial stock. **Agregar opciones como talla o color** opens the option editor. Once there are options, the generated combinations copy the price and initial stock typed before (never the SKU), the product form stops showing SKU, prices and stock, and the seller adjusts rows one by one or in bulk by value. Combinations she does not sell are removed before saving. Saving opens the product.
- **Product page** (`/products/:productId` on web): the same Variants card as creation. **Guardar cambios** (web) or **Guardar** (mobile) saves everything edited on the page together: options, values, order, new variants, removals, prices and SKUs. It saves all or nothing. Stock of saved variants is read-only.
- **Marks:** «Nueva» (not yet saved), «Desactivada», «Se quitará» (an unsaved thing the seller removes) and «Se eliminará» (a saved thing deleted on save). Removed rows keep an **Deshacer** until saving.
- **Variant detail** (web `/products/:productId/variants/:variantId`, mobile full screen): exists only for products with options. It shows the combination (read-only, with **Cambiar combinación**), sale price, purchase price, read-only stock, SKU, the QR with **Imprimir**, **Desactivar variante** / **Activar variante** and **Eliminar variante**, or the first reason it cannot be deleted (orders, stock, only variant). **Guardar cambios** saves only that variant's prices and SKU. Changing the combination, deactivating, activating and deleting are saved when confirmed. Unsaved new variants have a detail too (a dialog on web, a screen on mobile) that edits the row and offers **Quitar**.
- **Reordering:** web options and values move by dragging or with the arrow keys on the focused handle. Mobile has no drag in this version: the handle opens a menu with **Subir** and **Bajar**, and screen readers get the same two actions. Reason: a long-press drag conflicts with scrolling and is not accessible; the menu is the same on both platforms for screen readers.
- **Photo:** uploaded before saving through the image API, then only `imageId` is sent. It can be replaced or removed; removing does not delete the stored file. Mobile can pick from the gallery or take a photo; a denied camera permission keeps the form and allows the gallery. There is one photo per product.
- **Printing:** the label carries the product name, the combination, the SKU and the QR; if the content does not fit it is not printed. Mobile (Android, Brother printer) prints from the print sheet of the product page, which lists each variant by combination, marks inactive ones and can print them; opened from a variant detail it comes with that variant selected. Web prints the label of a variant from its detail through the browser print dialog; web has no label for products without options.
- Both platforms ask for confirmation before discarding unsaved changes (leaving, cancelling, reloading); closing the browser tab shows the browser's own warning.
- **Nueva venta:** offers only active variants and products with at least one, with options and values in saved order. An item whose variant was deactivated while the sale was being built returns to review marked «L / Azul ya no está disponible.».

## API

`/api/products` requires a session (Bearer token for mobile, cookie for web) and an active company. Responses carry `Cache-Control: no-store`. Request bodies are strict (unknown fields are rejected); responses are tolerant and may gain optional fields, which shipped clients ignore. A variant status other than `active` is shown as inactive.

| Operation | Route | Success |
| --- | --- | --- |
| List | `GET /api/products?search=&page=&pageSize=` (page size default 20, max 100) | `200 { items, page, pageSize, total }` |
| Detail | `GET /api/products/:productId` | `200 { product, image? }` |
| Create | `POST /api/products` | `201 { id }` |
| Save the editor | `PUT /api/products/:productId` | `200` detail |
| Edit a variant's price and SKU | `PATCH /api/products/:productId/variants/:variantId` | `200` detail |
| Change a combination | `PUT /api/products/:productId/variants/:variantId/combination` | `200` detail |
| Set a variant's status | `PUT /api/products/:productId/variants/:variantId/status` | `200` detail |
| Delete a variant | `DELETE /api/products/:productId/variants/:variantId` | `200` detail |

- There is no product-level `PATCH`: the editor sends the whole desired state with `PUT`, and single-variant fields go through the variant routes. Reason: partial product patches cannot express option and variant changes atomically.
- **Create** takes the ordered options (with client-generated UUIDs for options and values) and the variants as lists of value ids. A product without options sends `options: []` and one variant with `values: []`. Mobile generates the product UUID; core generates variant ids and QR codes. A second `POST` with an id already used returns `409 PRODUCT_ID_CONFLICT`, whatever the body. Reason: a retry after a lost response cannot create a duplicate product. Mobile shows the conflict and offers to review the list.
- **Save** carries the structure version, the full ordered options (an option omitted from the list is deleted; a new option for a product with variants names the value existing variants receive), the price and SKU of the saved variants whose price or SKU the form edits, the new variants, and the ids of deleted variants. Core applies a diff in bulk with a fixed number of statements, whatever the variant count.
- Every write answers the full product detail built after the write, with `hasOrders` per variant, so clients replace their state without another read.
- Errors use the shared `{ code, error }` envelope; field errors add `issues` with scope (product, option, value, variant or new variant), field, position and typed reason, so the client chooses the visible message by code and reason, never by the `error` text. All issues detectable together are reported together. Status mapping, codes and reasons are defined in `shared/contracts/products.ts` and `apps/core/src/features/products/presentation/api-errors.ts`.
- Ids that belong to another product or are repeated in the request are `422` issues with reason `ID_CONFLICT`; a primary-key race at write time is `409 ID_CONFLICT`.
- Mobile writes are online only and never retried automatically; after an uncertain result the screen offers **Recargar producto** or **Recargar variante**, and repeating status, combination or delete has no further effect.

## Concurrency

- There are no edit locks. Every structural write (create, a save that changes options, values or variants, changing a combination, deleting a variant) increases `structureVersion`. A save sent with an older version is rejected with `409 PRODUCT_CHANGED` and writes nothing; the form stays intact and offers **Recargar producto**. Prices, SKUs and status changes do not increase it, so they stay last-write-wins. Reason: concurrent editing of one product is rare, but an editor working from a stale structure would delete or recreate other people's variants.
- Writes lock the product row, so two actions on one product run one after the other. Editing transactions have an explicit timeout (`PRODUCT_WRITE_TRANSACTION_TIMEOUT_MS`, default 10 s) with a lower PostgreSQL lock and statement timeout; a timeout or lock conflict answers `503 SERVICE_UNAVAILABLE`.
- Deactivating a variant and creating an order in the same instant are not serialized: the order is equivalent to one created just before.
- The final guard against deleting a variant that has orders is the database foreign key from order items to variants, which restricts deletion.

## Observability

Writes log `product_created`, `product_saved`, `product_variant_updated`, `product_variant_combination_changed`, `product_variant_status_changed` and `product_variant_deleted` after commit, and `product_save_rejected` / `product_variant_action_rejected` for business rejections. Technical failures log `product_save_failed` or `product_variant_action_failed` with the stage once, and a failed reload after a committed variant action logs `product_variant_action_reload_failed`. Logs never contain names, SKUs or prices.
