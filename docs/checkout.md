# Checkout

The checkout is the public page where a buyer reviews an existing order, completes their details and delivery, confirms the purchase and pays, from a mobile browser without an account or app.

Code: `apps/core/src/features/orders/` (domain `checkout.ts`, application `checkout.ts`), `apps/core/app/routes/checkout.tsx`, contracts in `shared/contracts/order-checkout.ts`. Store appearance (logo and themes, shared with the public catalog): `apps/core/src/features/store-appearance/`, theme values in `shared/store-themes.ts`, contract in `shared/contracts/store-appearance.ts`, mobile editor in `apps/mobile/src/features/store-appearance/`.

## Business rules

### Link and access

- Every order is created with its checkout enabled (`Order.checkoutEnabledAt` is its creation time), whatever its origin: web, mobile, WhatsApp message or public catalog. A data migration gave every order without the date its creation time, cancelled and completed ones included; cancellation still takes precedence in the [state](#checkout-states), so their state did not change. Reason: the seller shares the link right away, with no prior step, and every order follows one invariant (rejected: a «Obtener enlace» step that enabled the checkout on request).
- The checkout lives on the store's brand host: `https://{subdomain}.{CATALOG_BASE_URL host}/checkout/:orderId` (production `https://{subdomain}.yoyos.lat/...`), built from the company's current [catalog subdomain](public-catalog.md#link-rules). Reason: the buyer stays at the store's address from the first product to the payment (rejected: keeping it on `app.yoyos.lat`, which takes the buyer off the store's address at the payment). The [public catalog](public-catalog.md)'s **Continuar** opens it on the same host, and the checkout's screens, steps and rules are the same for catalog orders.
- `app.yoyos.lat` does not serve the checkout or the buyer APIs: they answer 404, with no redirect from links built for the app host. Reason: keeping both hosts would mean two origins for the buyer APIs (rejected: redirects or a period when both hosts work).
- The subdomain is not mandatory: a company without one has no order link until the seller chooses its catalog link in «Apariencia de la tienda». Its orders are already enabled, so every one of them shows its link as soon as the subdomain is saved, with no other step. Reason: the link is the seller's brand decision and the step already exists (rejected: assigning a subdomain at sign-up or by migration, which takes that decision from the seller and can take a name another store wants; keeping these companies' checkout on `app.yoyos.lat`, which brings back two origins; showing a disabled or empty link, which does not say what to do).
- The checkout works on the brand host whether the catalog is published or hidden; a saved subdomain is enough. Reason: hiding the catalog closes the shop window, not the sales already shared by link (rejected: requiring a published catalog, which ties link sales to the shop window).
- The URL carries no company: the company comes only from the brand host, and the order is looked up by its id under that company. On a published brand host, a link whose order is unknown, malformed, of another company or not enabled shows "Enlace no disponible". The former `/checkout/:companyId/:orderId` shape is not served and shows the same page. On an unavailable host (unknown, released or unowned reserved subdomain, or a hidden catalog), any `/checkout/...` that is not an order of the host's own company answers the same byte-identical «Catálogo no disponible» (404) as every other path there ([Public catalog · Brand host](public-catalog.md#brand-host)). Reason: an invented URL never reveals whether a company is behind a host; only someone with a valid link sees the store's checkout (rejected: a checkout-specific "not available" on a hidden host, which would tell it apart from an unknown one).
- Changing the subdomain releases the previous one with no redirect, so links already shared stop working; the change confirmation warns about it ([Public catalog · Saving, changing and failures](public-catalog.md#saving-changing-and-failures)). The seller panel always builds the link from the current subdomain, so it can be shared again. If another company later takes the released subdomain, an old link reaches a host whose company does not match the order and is not available. Reason: changing a link is rare (rejected: redirecting or keeping the previous subdomain, which another store may take, and blocking the change while orders are pending).
- The link does not expire and is not closed by payment, shipping or delivery. Reason: confirming and paying are independent actions; closing by shipping was rejected.
- The URL is the access credential. The order id is a random, globally unique UUID; the visible order number is never used to resolve access. No signed token, extra key or link table is used. Reason: the UUID is unguessable and avoids extra state (rejected: `/checkout/:token`).
- The URL scope never grants access to private seller routes. Tenant isolation (RLS) still applies: the server sets the brand host's company as the tenant, then reads the order by id under it and checks that its checkout is enabled.
- An invalid, unknown or not-enabled link shows the same message, "Enlace no disponible", without revealing whether the order exists.
- Responses are sent with `Cache-Control: no-store` and `Referrer-Policy: no-referrer`, and the page is `noindex`.
- `/pago/:orderId` does not exist. Reason: it resolved access with the order UUID alone; every buyer goes through the checkout.

### Order link (seller)

- **Web order detail:** the «Enlace del pedido» card, beside the customer. It shows the buyer's state line («Confirmado por el comprador», or «Pendiente de confirmación» only while the order is active), a read-only input that always holds the absolute brand-host URL, an icon button to copy it and one to open it in a new tab, and «Comparte este enlace con el comprador para que confirme y pague.». The page's loader builds the URL, so showing it costs no request of its own. Copying announces «Enlace copiado» politely; a copy the system refuses fails silently, like the catalog link. There is no «Obtener enlace», «Copiar enlace» text button or «Abrir checkout del pedido» link. Reason: the seller sees, copies and opens the link at any time, without a prior step.
- **Without a subdomain:** no input or icons, but «Elige el link de tu tienda para compartir este pedido.» and **Ir a Apariencia de la tienda**, which opens the editor at the **Publicar catálogo** card (`#catalog-publication`), the same destination Settings → Catálogo uses. Reason: it tells the seller exactly what to do, when they need it, through a step that already exists. A failed read of the subdomain shows an error with **Reintentar**.
- **Cancelled order:** the card keeps only «Pedido cancelado», with no input or icons, on web and mobile. Reason: sharing a link that cannot be used only confuses the buyer (rejected: the full card, which invites sharing it). A buyer who already has the link sees the themed «Pedido cancelado» / «Este pedido ya no puede confirmarse. Contacta al vendedor.» screen, never "Enlace no disponible", and confirmation and payment stay blocked.
- **Mobile:** the order detail loads the link when the screen opens and on every return (a subdomain may have been chosen meanwhile) with `POST /api/orders/:orderId/checkout-link`, an idempotent read: a plain tenant-scoped read with no write or row lock, so it never holds back a buyer confirming. It answers the brand-host URL, `409 SUBDOMAIN_REQUIRED` without a subdomain (the screen shows the same text and **Ir a Apariencia de la tienda** with `focus=catalog`) or `409 ORDER_CANCELLED` (the screen offers no link action for a cancelled order). The link offers copy, share and open, with touch targets of at least 44 px. Older app builds show their generic «No se pudo obtener el enlace…» for `SUBDOMAIN_REQUIRED`. Accepted: the seller updates the app.
- **Order lists (web and mobile):** «Pendiente de confirmación» describes only an order that is still active and not confirmed; a completed order that was never confirmed shows no checkout label, a confirmed one «Confirmado por el comprador» and a cancelled one «Pedido cancelado». The mobile history's checkout shortcut follows the same rule and is never offered for a cancelled order. Reason: every order is enabled, so «pending» would otherwise mark finished orders as waiting for the buyer.

### Checkout states

The state is derived from `Order.checkoutEnabledAt`, `Order.checkoutConfirmedAt` and cancellation; no separate status column is stored. A confirmation date requires an enabled date. The enabled date stays nullable in the database, although every order has one. Reason: no constraint is added on the order table during a rolling deploy.

| State | Behavior |
| --- | --- |
| Not enabled | Only an order without an enabled date, which no order has after creation and the migration. No public access; the seller read answers "not available". |
| Pending | Shows products and amounts; the buyer can complete or correct their details and delivery, then confirm. |
| Confirmed | Read-only details; the page then shows one of the [payment screens](#payment-screens). Repeating the confirmation returns the existing result without overwriting anything. Confirming shows no success block: arriving at the payment step is the feedback. Reason: a success message about confirming pulls attention from the amount to pay on the very screen where the buyer pays; changes are asked for in the chat the buyer already uses. |
| Cancelled | Takes precedence over the other states without clearing their dates; confirmation is blocked. |

The order title is always followed by «Revisa los productos y el total de tu pedido.». The slot under it holds the «Pedido cancelado» block when cancelled and the [closing card](#payment-screens) while a receipt is pending, and is empty in every other state.

### Confirmation

- Requires a non-empty name and a phone in international format (see [Buyer and recipient](#buyer-and-recipient)). No surnames or minimum word count are required.
- Products and quantities are set by the seller; the buyer cannot edit them. To change products, the order is cancelled and a new one is created.
- The buyer either keeps the current delivery or replaces it with one of the [offered](#delivery-choice) delivery methods; the server resolves its price from the company's delivery settings (`apps/core/src/features/delivery-settings/`) and rejects it if the price the buyer saw changed.
- The buyer sends the total they saw (`expectedTotal`). It is compared with the current total under the order lock; if it differs, nothing is saved, the form keeps its values and the new total is shown for a new confirmation. Reason: the buyer never confirms an amount they did not see; the sent value is never used as a price.
- Buyer, delivery change and confirmation date are saved in one transaction that locks the order. Concurrent confirmations are serialized; only the first one writes.
- Confirming expresses purchase intent. It does not register a payment.
- Confirming does not touch the catalog's cart, which lives on the brand host's origin. The catalog asks core whether its continued order was confirmed and empties the cart itself ([Public catalog · Buyer](public-catalog.md#buyer)).
- The buyer is stored in `OrderBuyer`, a per-order copy (see `apps/core/prisma/schema.prisma`). Editing it never updates the global Contact. `contactId` comes from the server, never from the public form.

### Buyer and recipient

- «Tus datos» asks for «Nombre» and «Teléfono», then the check «Otra persona recibe el pedido», unchecked by default, with «Si no lo marcas, entregamos a tu nombre y teléfono.». Reason: the buyer types their name and phone once instead of again as the recipient's.
- **Unchecked:** the delivery's recipient is the buyer's name and phone in every delivery method (home, agency, pickup) and when the saved delivery is kept. **Checked:** «Nombre de quien recibe» and «Teléfono de quien recibe» appear and are required, validated together with the buyer's fields so all errors show at once; the buyer stays as typed.
- The check appears in every delivery method, including «Conservar entrega actual». A saved delivery whose recipient name or phone differs from the buyer's (phones compared normalized) opens with it checked and the fields prefilled; otherwise it opens unchecked. The kept-delivery summary shows who receives.
- The server enforces it on confirmation: unchecked, it ignores every recipient field the client sent and uses the buyer's name and phone; for a kept delivery it changes only the recipient's name and phone (address, method, rate and document unchanged). A kept delivery that already progressed keeps its recipient and the confirmation still goes through. Reason: a hidden or stale field must never fail or change a delivery that goes to the buyer.
- The check and the kept delivery's recipient travel only with the form and are never stored; the stored recipient keeps its shape (`recipientSchema` in `shared/contracts/orders.ts`). Agency delivery still asks for the recipient's identity document in both cases.
- **Phone:** the buyer's and the recipient's phones have a country selector with the full country list, Peru (+51) by default, and the number is typed in national format without the code («977 909 427»). The closed selector shows the ISO code and calling code («PE +51»). The phone is stored in E.164 without spaces («+51977909427»), which `internationalPhonePattern` validates (`shared/phone.ts`). A saved phone is split back into country and number by the longest matching calling code; one that is not E.164 shows its digits under Peru. Typing or pasting a number that starts with «+» splits it into country and number. Shared calling codes use their main country (United States for +1, United Kingdom for +44, Russia for +7). Country names come from the browser and are added only after the page loads, so server and browser render the same.
- **Known phone debt:** only the E.164 shape is checked (8 to 15 digits), with no per-country length or trunk-prefix rules; and territories of the North American plan carry their area code in their calling code (Jamaica «+1876»), so their national number is the 7-digit local one. Accepted: the scope is the international format, and per-country validation would need a phone metadata library on the buyer's phone.

### Delivery choice

- «Forma de entrega» offers, in this order and only when offered: «Conservar entrega actual» (only with a saved delivery), «Entrega a domicilio», «Envío a agencia» and «Recojo en tienda · Gratis». A saved delivery is preselected; otherwise the first offered method, so a store with home on but without home coverage opens on «Envío a agencia» when agency is covered, otherwise on «Recojo en tienda · Gratis».
- «Entrega a domicilio» and «Envío a agencia» each appear only when the method is on and has [coverage](delivery.md#delivery-methods) (department-bounded for agency). A switched-on method without coverage is not shown, and the seller sees the coverage warning in settings. Reason: every district would end in «No hay opciones de envío…» or «No hay agencias disponibles…».
- **Covered places:** the checkout receives, per offered method, only the covered departments, provinces and districts, as canonical codes (a whole department or province travels as one code, never expanded into districts), decided when the checkout loads; they are not refreshed while the page is open. Zone names, options, prices, couriers and agencies are never exposed; rates and agencies come only from the quotation of a chosen district. Reason: it is the minimum the filter needs, and the same places are already discoverable by quoting district by district with the order link (rejected: keeping a yes/no flag and only changing the empty-quotation message, which leaves the buyer finding out after picking). A projection that fails its contract shows the page's load error, never «no coverage».
- When no method is offered and there is no saved delivery, the buyer sees «No hay modalidades de entrega disponibles. Consulta con la tienda cómo recibir tu pedido.» and confirmation stays disabled.
- **Location:** Departamento and Provincia side by side, then Distrito at full width; each is a combobox where the buyer types to filter and picks in the same control, by keyboard or touch. Options show names only, matched without case or accents with the match in bold; the district code (ubigeo) is never shown or searchable and travels only to the quotation. Changing the department clears province and district; changing the province clears the district. The seller's district selector on web is the same combobox, with the whole country ([Delivery](delivery.md#assigning-delivery-to-an-order)). Reason: one control to find and choose instead of a search field plus a list, and the ubigeo means nothing to a buyer.
- **Offered places:** under home or agency the comboboxes list only the places that method covers: Departamento the departments with at least one covered district, Provincia the provinces of the chosen department with a covered district, Distrito the covered districts of the chosen province. A whole department in a zone offers all its provinces and districts (including districts the catalog adds later); a whole province offers its department with only that province (plus any other covered one); loose districts offer their department and province with only those districts. Several zones offer the union, each place once. Each method offers its own places: with home only in province Lima and agency only in Arequipa, home lists Lima → Lima → its 43 districts and agency only Arequipa. Reason: every district the buyer can pick gives at least one home rate or one agency in the list.
- **Hint:** one hint for the location group, right under «Distrito de entrega» and before Departamento, always shown whatever the size of the coverage: «Escribe para buscar. Solo aparecen los lugares donde la tienda entrega; si el tuyo no está, consulta con la tienda.». Screen readers read it as the description of Departamento only. It names no channel and assumes no earlier conversation, so it fits a buyer from the chat and one from the public catalog. Reason: the catalog and the checkout have no contact button by decision ([Public catalog](public-catalog.md)), and no «not in the list» flow is offered.
- **Empty search** inside the list: «Ningún departamento de la lista coincide. Revisa cómo lo escribiste.», «Ninguna provincia de la lista coincide. …», «Ningún distrito de la lista coincide. …». Reason: the cause may be a typo, and the hint already says only covered places appear, so the text never claims the store does not deliver there.
- **Preselection:** when the location fields appear (page load or entering home or agency) and when an upper level gets a new value, every level below with exactly one offered choice is set, top-down, stopping at the first level with several. A preselected district starts its quotation at once, as a pick does, and stays visible in its field. Clearing a level never triggers it: a cleared level stays empty until the buyer picks again or enters the method again, and choosing the value an upper level already has changes nothing. Preselected values keep their label and focus ring, and tabbing from the methods reaches Departamento first. Reason: the buyer's action is respected and nothing is quoted without them, while single choices are not asked for.
- **Entering home or agency** from any other method (home ↔ agency, store pickup, «Conservar entrega actual», **Pasar a Entrega a domicilio**): rate, agency and quotation are cleared; the current district stays if the new method covers it and is quoted again. Otherwise it is cleared, the deepest covered level above it stays (department or province), and preselection runs. The current district is the last state of the form's district: the one last picked under home or agency, else the saved delivery's, else none; an explicit clear counts, so the saved district does not come back. Department and province survive store pickup and «Conservar entrega actual». Reason: a kept but uncovered district would lead straight to a dead end.
- **Location notice:** one space under the delivery methods and above the location fields, taking no space while empty, showing at most one message chosen by the last location event (the fields appearing or an upper level getting a new value):

  | What the event did | Message |
  | --- | --- |
  | Cleared the buyer's district, preselected nothing | «Envío a agencia no llega a Miraflores. Elige otro distrito.» |
  | Cleared it, preselected some levels, district still empty | «… no llega a Miraflores. Completamos los campos que tienen una sola opción; elige tu distrito.» |
  | Cleared it and preselected a district in its place | «… no llega a Miraflores. Completamos los campos que tienen una sola opción.» |
  | Preselected levels, nothing cleared | «Completamos automáticamente los campos que tienen una sola opción.» |
  | Neither | Empty |

  The method is named as in the method list and the district in title case, whatever its source (a pick or the saved delivery). A pick or clear that triggers no preselection empties it, and store pickup or «Conservar entrega actual» hide the fields and empty it. Cleared-district messages are a padded muted block like «No hay opciones de envío…»; the preselection message has the hint's look; neither relies on color alone. The notice and the quotation status «Consultando opciones de envío…» are separate polite live regions present before their text, never move focus, and the notice is announced before the status. Reason: two notices or a stale one would contradict the fields and be announced over each other.
- The hint, notice, empty-search and no-method texts have Portuguese versions in the checkout's locales and are styled by the five themes with the contrast floor. The seller's location fields keep their own hint, empty text and full country list.
- Home and agency quote the buyer's district with the [current quotation](delivery.md#quotation). «Entrega a domicilio» lists only home rates; «Envío a agencia» has no rate list: the buyer picks a destination agency and its rate follows from it.
- The agencies offered are only those of the agency rates of the buyer's district. Their price is the option's, never the agency's location. Reason: coverage and price are per zone; a district whose zones have no agency option sees no agencies, even with agencies nearby. A district is offered under agency only when an eligible agency of a covering option sits in its department, so the cascade below always finds one.
- An agency in several options is shown once with the lowest price; on equal price, the option whose name sorts first. Reason: the buyer picks a place, not an option.
- **Location cascade:** one list with the first level that has agencies, by the agency's location: the buyer's district, else their province, else their department. A notice names the level used when it is the province or department. Levels are never mixed and agencies outside the buyer's department are never shown. Reason: shows the nearest agencies without maps or geolocation.
- Within the level, agencies are ordered by price, agency name, then courier name. Each entry shows agency, courier, address, district, province and price. A single agency is preselected.
- Without agencies at any level the buyer sees a message with **Cambiar distrito** and, when «Entrega a domicilio» is offered, **Pasar a Entrega a domicilio**. This and «No hay opciones de envío para este distrito…» are reached only when coverage changed after the page loaded; the server quotes and confirms with its own rules ([Delivery · Quotation](delivery.md#quotation)), which are not department-bounded for agency.
- Changing department, province or district clears the agency and rate and quotes again. Changing method follows «Entering home or agency» above.
- A kept delivery is offered and preselected with its summary, rate and amount, and confirming with it is accepted, even when its district is no longer covered or its method is no longer offered. Reason: it is an agreement already recorded in the order.
- The agency delivery cost is shown with the chosen agency, in each destination entry and in the summary's «Entrega» row, never on the «Envío a agencia» option itself, since it depends on the agency. No delivery lead time is shown for any method. Reason: Yoyos records no lead time, and adding one would change the delivery settings on web and mobile.
- On a phone, in every theme, labels sit above their fields and the total is visible before the payment action.
- Agency delivery requires the recipient's identity document. The server revalidates option and agency on confirmation; the cascade and its level are not stored.
- The delivery section asks for no recipient name or phone of its own: they come from «Tus datos» ([Buyer and recipient](#buyer-and-recipient)).

### Amounts

- The checkout shows `itemsTotal` (products) and `total` (the order total, including delivery). It never recalculates the total in the browser nor labels the subtotal as total; `paidAmount` and `balanceDue` come from core.
- Other modules update the authoritative order total; payments change the balance, not the total.
- **Summary card:** «Subtotal de productos», «Entrega» and the total row. Before confirming the total reads «Total a pagar»; in every confirmed state it reads «Total del pedido» (also the section's accessible name). Reason: the page never shows two different amounts labelled as «to pay»; the only amount due is in the payment box. The card is visible on phones below the main column in the confirmed states (sticky only on a computer) because it is the only place that shows the delivery charge.
- **Amount rows**, in the payment box and in the separate amounts card, depend only on whether something was confirmed, never on the delivery charge (there is no «Incluye entrega» row):
  - Nothing confirmed: one row. «Monto a pagar» (the balance, equal to the total) in the payment box; «Total del pedido» in the amounts card, where nothing can be paid.
  - Something confirmed: three rows that read as a subtraction: «Total del pedido», «Pagado», «Saldo pendiente» (emphasized in the payment box). An overpayment shows the real «Pagado» and a «Saldo pendiente» of S/ 0.00, with no notice for the buyer.
  - «Pagado» counts only payments the seller confirmed (an approved receipt or a recorded payment); pending, rejected and voided ones do not. Reason: two equal amounts plus a delivery line read like a wrong sum; three rows read as a subtraction.

### Payment

- Payment is only available once the checkout is confirmed and the order is not cancelled. The buyer payment API (`/api/buyer/orders/:orderId/...`) rejects orders that are not enabled, pending or cancelled. Its view carries, per payment, the report date (`reportedAt`, `null` only for a manual payment).
- The company's offered payment methods are shown: bank transfer, with its image when uploaded, and a digital wallet with provider, holder and its payment QR. A wallet is offered only when its QR passed the check of [Payment methods](#payment-methods) and its image URL resolves; otherwise it is left out instead of failing the page. Without any offered method the buyer sees the no-settings text.
- "Ya pagué" requires a JPG, PNG or WEBP receipt up to 10 MB. The report is idempotent on retry and stays pending review; only the seller's approval records the amount received ([Orders · Payments](orders.md#payments)).
- While a report is pending the page shows the [closing screen](#payment-screens) instead of the payment step and offers no upload. Reason: one report under review at a time keeps the seller's list readable, and the buyer cannot pay twice by mistake. A wrong screenshot is solved in chat: the seller rejects it and the buyer sends another. A receipt never changes the balance or «Pagado»; only the seller records money received.
- When no report is pending, the balance is above zero and the buyer's most recent report was rejected, the upload block returns with «Tu comprobante fue rechazado», «Motivo: …» when the seller gave a reason, and «Envía otro comprobante para que la tienda lo revise.» as its first part, always expanded with the block. Sending another receipt creates a new report and replaces the notice with the pending one. A retried «Ya pagué» of the rejected report shows the rejection, never a false pending state, because the page always shows the refreshed buyer view. Reason: the buyer learns what to fix without another chat message.
- «Comprobantes enviados» lists every receipt as «Ver captura · <estado>» (Pendiente, Confirmado, Rechazado, Anulado), with the reason below a rejected one. It appears in the payment step, the paid state and the not-available card, not in the closing screen. A receipt still pending when the order became paid keeps «Pendiente».
- The buyer is not notified of a rejection outside the checkout; the seller tells them in chat.

### Payment screens

One pure function (`checkoutScreen`, `apps/core/src/features/orders/presentation/buyer-checkout-screen.ts`) derives the screen from the checkout state and the buyer payment view; no part of the page decides it again. No new state is stored. Precedence:

1. Cancelled → «Pedido cancelado» only.
2. Payment not available (delivery awaiting a quote) → the not-available card. Dormant today: the buyer view always reports payment as available, and it keeps its place only to preserve the branch.
3. Paid (confirmed payments cover the total, overpayment included) → «Pedido pagado» / «El pago de este pedido ya está confirmado.» with the amounts card and «Comprobantes enviados». A pending receipt or a manual payment covering the total wins over the closing screen.
4. A receipt pending review → closing screen.
5. Otherwise → payment step, with the rejection notice when the latest report was rejected.

**Closing screen** (shown on the same order link, with no URL of its own, so a reload or another device shows it while the receipt is pending): the card sits under the order title on every width, followed by the products, «Datos del comprador» and the summary. Reason: a buyer reopening the link on a phone reads the reassurance first. The card uses the theme's information colors with a clock icon, never success styling or approval wording. Reason: success on an unreviewed receipt reads as «paid». It shows «Recibimos tu comprobante», «La tienda revisará tu pago y te confirmará cuando lo reciba. No necesitas hacer nada más por ahora.» and «Si enviaste una captura equivocada, escríbele a la tienda por donde hiciste tu pedido.», then **Ver captura** for every pending receipt, newest first.

- **Ver captura** opens the receipt in a new tab, with an external-link icon, a touch target of at least 44 × 44 px and the accessible hint «(se abre en una pestaña nueva)». With more than one pending receipt each carries its send date and time in the store's zone (America/Lima, the seller's), whatever the buyer's device zone, formatted with the order list's medium date and short time («Ver captura · 30 oct. 2026, 6:42 p. m.»; Portuguese «30 de out. de 2026, 18:42»). Reason: buyer and seller name the same time for the same receipt. A pending receipt whose image does not resolve is listed as plain text (dated when there are several; nothing for a single one) and the closing screen still shows, since it depends on the receipt being pending, not on its image.
- The main column keeps only «Datos del comprador»: no payment methods, upload, pending notice, «Comprobantes enviados», «Monto a pagar», «Pagado» or «Saldo pendiente», even with earlier confirmed payments. Reason: the receipt does not change what is owed, and an unchanged balance reads as «your payment did not count».
- It ends when the seller approves or rejects the last pending receipt, or the order becomes paid, not available or cancelled. Rejected → payment step with «Tu comprobante fue rechazado». Approved below the balance → payment step with the three rows and the upload block, with no special notice. A void while a receipt is pending keeps the closing screen. Voiding the payment of a paid order brings back the payment step.

**Focus after «Ya pagué».** The screen shown always comes from the refreshed order state, never from the send response alone, so resending an already rejected report shows the rejection. Only on that transition focus moves to one heading of the refreshed page: «Recibimos tu comprobante», «Tu comprobante fue rechazado», «Pedido pagado» or «Pedido cancelado» (the block under the order title). The card holding that heading is not also a live region, so it is announced once. Opening or reloading the link moves no focus.

**Failures of «Ya pagué».** A failed or unanswered send keeps the buyer on the payment step with the screenshot ready and «No se pudo enviar el aviso. Tu captura sigue lista; vuelve a intentarlo.»; the retry reuses the same report and never creates two. A `409 ORDER_CANCELLED` from the send or from the follow-up read refreshes the page and shows «Pedido cancelado» with focus. If the report was recorded but the follow-up read of the buyer view fails, the upload block is replaced by «Enviamos tu comprobante, pero no pudimos actualizar la página. Recárgala para ver el estado de tu pago.» with **Recargar página**, focused and announced once; **Ya pagué** is not offered again. Reason: the route's error page would otherwise hide that the report arrived.

The buyer is not notified outside the page when the seller decides, and the closing screen offers no way to replace or withdraw the receipt. The mobile app has no buyer checkout and is unaffected.

### Payment methods

The seller configures the methods in web settings, «Medios de cobro»: a digital wallet (provider as free text, holder and «QR de cobro») and a bank transfer (bank, holder, account number, CCI and an optional image). Contract: `shared/contracts/payment-settings.ts`, served at `/api/company/payment-settings`. Mobile has no payment settings screen.

- **The wallet requires a payment QR.** A wallet that is offered must have an image in which Yoyos decodes at least one QR; a wallet that is not offered needs nothing. The QR content is not compared with provider or holder. Reason: a wallet without a QR leaves buyers asking where to pay. Bank transfer is unchanged: its image stays optional and is not checked, because bank data is enough to pay.
- **When it is checked:** when the seller chooses a new image (`POST /api/company/payment-settings/qr-checks`, which only informs the page and stores nothing) and again on saving it, which is the check that counts. A save whose wallet image is the one that already passed is not read again, so a checker outage never blocks unrelated edits such as the bank account. Any client saving payment methods gets the same rejection.
- **Validity is stored with the wallet**, as the image id that passed (the same image id always holds the same bytes). A wallet saved with a QR that passed stays offered and shown as valid until the seller changes its image; a later checker outage never hides it.
- **Failures:** an image without a QR answers `400 INVALID_PAYMENT_QR`; a checker, image storage or capacity problem answers `503 QR_CHECK_UNAVAILABLE`; a missing image or one of another company answers `400 INVALID_INPUT`. Nothing is saved on any of them; a save is a full replacement, so repeating it never duplicates anything.
- **Bounded checks:** each web process runs at most `PAYMENT_QR_CHECK_SLOTS` checks at once (default 2) and answers busy instead of queuing; the image read is abandoned after `PAYMENT_QR_CHECK_READ_TIMEOUT_MS` (default 10000). Reason: a check can hold about a hundred MB and block the event loop of the process that also serves every checkout.
- **Wallets saved before the QR requirement** are read as unchecked: not offered to buyers until the seller saves them and their image passes the save check. There is no install-time check or data migration. Reason: a one-time check would run in the release, which has no image storage and could stop every deploy, and no business operates in production. The panel says «Tus compradores no ven esta billetera hasta que la guardes con un QR válido.» (with image, save enabled) or «… hasta que subas un QR válido.» (without image, save disabled until a QR is uploaded or the wallet is unticked).
- The page disables **Guardar cambios** while an offered wallet has no QR, while the chosen image is not a QR, and while the image uploads or is being checked; it stays enabled when the choose-time check could not run, since the save check decides. Every error keeps what the seller typed.
- The [checkout preview](#preview) lists payment methods under the same offered rule, so the seller never sees a wallet buyers do not see.
- **Compact layout:** the payment methods' radios sit in one row; only the selected method's details are shown, in one block with its QR (about 136 px) beside the data, which are only the fields that exist (wallet: provider and holder; transfer: bank, holder, account and CCI with their copy buttons), and the [amount rows](#amounts) under them. «Adjunta tu comprobante» is one dashed row on a computer (the file goes to a second line on a phone) with the chosen file's name, its size and a button to remove it. The separate amounts card appears only in the paid and not-available screens, where there is nothing to pay with. Every action and route stays the same in the five themes and in the «Apariencia de la tienda» preview. Reason: the payment step is much shorter on a phone (rejected: adding a wallet «Número» or renaming «Ya pagué» to «Enviar comprobante», which change the payment methods model or copy without a decision behind them).
- In the payment step, «Datos del comprador» shows two lines: name · phone, then the delivery method and where it goes (address and district, pickup address, or agency name and address).

### Order number

- Every order gets `Order.number`: a per-company sequence starting at 1001, shown as `Pedido #1001`. It continues past 9999 without fixed width, is permanent and is not reused after cancellation.
- It is allocated by atomically incrementing `Company.nextOrderNumber` in the same transaction that creates the order, and `(companyId, number)` is unique. Reason: `MAX + 1` or counting orders races under concurrency.

### Public projection

The public response contains the store name, order number, products, quantities, sale prices, `itemsTotal`, `total`, delivery, the buyer's available details and the checkout state. Each product carries `imageUrl`, the public URL of its product's current primary photo or `null` (see [Product thumbnails](#product-thumbnails)). It never includes internal costs, contact, seller or variant IDs, or payment records. Product photos are already public images (the catalog shows them), so the photo adds no internal data; the buyer only sees the photos of the products in that order.

The orders module offers two reads of the same projection: `orders.getCheckout`, used by the checkout page, which adds the item photos, and `orders.getCheckoutView`, without photos, used by the delivery quotation endpoint when it authorizes a quote by order link. Reason: a quotation never renders photos, so it does not pay for their lookup or log their failure.

## Appearance

Each company brands its store with a logo and one of five fixed themes: the store appearance, «Apariencia de la tienda». It belongs to the company, not to the seller or the order, and one appearance applies to both the checkout and the [public catalog](public-catalog.md#theme); there is no theme per surface. Reason: the store must look the same from the first product to the payment.

### What can be configured

| Element | Options |
| --- | --- |
| Logo | Upload, replace or remove. PNG, JPG or WEBP up to 10 MB and up to 8000 px per side and 24 megapixels, validated by content. No SVG, crop or positioning. |
| Theme («Tema») | Exactly one of **Clásico** (default), **Boutique**, **Antojo**, **Suave** and **Noche**. |

No value of a theme (color, background, accent, font, rounding) can be edited, and nothing else is configurable: no CSS, HTML, scripts, custom domains, per-surface or per-order settings. Reason: a closed set gives each business a distinct look while every option stays tested and accessible, and configuration can never break the buyer flow (rejected: free colors or per-company overrides).

The theme names are proper names, shown the same in every language. The interface always calls them «tema», never «estilo», «plantilla» or «diseño».

### Themes

- A theme is a closed set of colors, fonts, type sizes and weights, rounding, borders, shadows, spacing, logo plate, photo filter and product thumbnail shape. It changes styles only: the checkout's steps, fields, texts, validations and screen order are identical in all five, and the product thumbnail is the only content themes added. The catalog applies the same values over its own layout, except the field and button sizes, which stay the catalog's own ([public catalog](public-catalog.md#theme)).
- The five definitions live in code: `shared/store-themes.ts`, the single source of every theme value, read by core (the CSS variables of the checkout, the catalog and the editor preview) and by the mobile app (its static theme samples). Every color is an opaque HEX, so contrast is computable. Reason: contrast is verified in advance and no tone is computed at runtime, and both apps paint the same values. The contrast, completeness and font tests live in core (`apps/core/src/features/store-appearance/domain/store-themes.test.ts`), because the mobile typecheck covers `shared/` with Jest types only.
- Only the theme identifier is stored (`classic`, `boutique`, `antojo`, `suave`, `noche`), never its values. Reason: adjusting a theme applies to every company that uses it without migrating data.
- Adding, changing or removing a theme or one of its values is a reviewed code change, never a setting. A theme cannot inherit a value from another: each one defines every token.
- An unknown stored identifier makes the stored appearance unusable as a whole: checkout and catalog fall back to Clásico without logo, so both surfaces stay identical. The editor shows the same with a notice (see [Editing and publishing](#editing-and-publishing)).
- **Fixed mode:** Noche is always dark; Clásico, Boutique, Antojo and Suave are always light. Neither the buyer's system preference nor the stored panel preference changes them. Reason: the mode is part of each theme's identity and keeps one tested version per theme (rejected: light and dark versions of each theme). The fixed mode applies only to the themed buyer pages (checkout and catalog) and the editor preview; «Enlace no disponible», «Catálogo no disponible», the catalog's full-page load error, the seller panel and every other page keep following the system or stored preference.
- **Fonts:** Clásico uses the system sans. Boutique: Playfair Display for headings, Inter for the body. Antojo: Fredoka for headings, Nunito for the body. Suave: Outfit. Noche: Inter. All are free and self-hosted by Yoyos, and the browser downloads only the fonts the active theme renders. If a font fails to load, the text uses the theme's fallback system font with the same layout. Reason: no external provider or cost, and no weight from unused fonts on the buyer's phone.
- **Serif only for display text in Boutique:** headings, the store name, product names and the «Total a pagar» label use the heading font; field labels, typed values, buttons, prices and every amount (including the total amount) use the sans body font. Reason: serif harms the reading of data and numbers on a phone.
- **Antojo's primary button** is coral with dark brown text. Reason: white on coral reaches only 3.1:1; dark brown keeps the coral identity above 4.5:1.
- **Semantic colors** (errors, warnings, success, information, payment states, destructive actions) keep their meaning and icons in every theme, in tones that meet the contrast floor on that theme (dark-surface tones on Noche). «Gratis» uses the theme's own free color.
- **Payment images and QR codes** keep their original colors and sit on a white plate in every theme, so a QR stays scannable on Noche. Receipts are text links.
- The selected payment method's block (QR, data and amounts) is a store part of its own, `payment-details`, so themes style it; in its narrow column the «Monto a pagar» label wraps instead of crossing the QR in display fonts such as Antojo's.
- The «Otra persona recibe el pedido» checkbox sits beside its label and is filled with the theme's strong accent when checked, in every theme.

### Contrast floor

- In all five themes: text at least 4.5:1 against its surface (background, every stop of Suave's gradient, cards, fields, selected options); borders of fields and controls, the selected option, radio dots, invalid-field borders and the keyboard focus at least 3:1 against card, background and field surface. Decorative borders, separators and shadows only need to be visible.
- Text styled as muted or secondary (including the closing card's receipt entries over the information surface) must still meet the 4.5:1 floor on its surface: no reduced opacity on text, since it lowers contrast below what the theme tokens were verified for. The closing card's information colors meet the floor in all five themes.
- The payment method chips' own border is decorative in Boutique and Noche: each chip holds a radio whose border passes 3:1, and the selected chip adds its outline. In the other themes the chip border is a control border.
- A unit test checks every pair for every theme.
- When an approved reference value failed the floor, the floor won: only that value moved, keeping hue and chroma (OKLCH) and changing lightness until it passed. Each adjusted value carries its original in a comment in the themes file. Reason: keeps each approved look while meeting the floor, with no large-text exception for buttons.

### Logo presentation

- The logo is always shown whole: never cropped, distorted or recolored. It sits on a white plate in every theme, so dark, light and transparent logos read the same way, including on Noche. Reason: a logo that cannot be read defeats the purpose of branding.
- Each theme sets the plate's size, rounding, border, shadow and placement: Clásico and Noche at the start with 8 px rounding; Boutique centered above the store name with square corners; Antojo at the start on a pill plate with a hard shadow; Suave centered on a pill plate with a soft shadow. A pill plate is a circle for a square logo and a capsule for a horizontal one, so a long logo is never cut. A long horizontal logo may widen its plate up to 20rem so it can fill the plate's height; on a phone the plate leaves about 6rem beside it for the store name (Boutique, where the name sits below, may use the full width). Reason: an 8:1 wordmark capped at the square logo's width is legible only at about 8 px. In themes with a centered header, the brand is centered within the page width.
- Without a logo, or when it fails to load, the store name alone identifies the business; no initials mark is invented.

### Product thumbnails

- Each product row of the checkout shows, at the left, a thumbnail of the product's current primary photo, then name, variant, quantity by price and subtotal. Size and shape per theme: Clásico 56 px square, Boutique 56 px at 4:5, Antojo 76 px square, Suave 64 px square, Noche 48 px square, with the theme's rounding, border and photo filter.
- The photo is the current primary (first) photo of the item's product (see [Products · Photos](products.md#photos)), resolved through the item's variant whatever the product or variant status; only that one photo is read, never the product's whole list. It is not copied into the order: changing the primary or removing it changes it in open links, next to the product name the order keeps. Reason: the photo is presentation, not part of what was agreed.
- A product without photo, a deleted variant, or a photo that fails to load shows a neutral block of the same size and shape with the first letter of the product name saved in the order, in capitals («Polo básico» → «P»); never a broken image.
- The thumbnail is decorative: the name next to it identifies the product, so it adds nothing for screen readers.
- If the photos cannot be read, the checkout loads with markers in every row. Reason: photos are decorative and must never block a sale.

### Default

Clásico is the default: a company that never saved an appearance is on Clásico without logo, in checkout and catalog. Reason: Clásico is neutral for any brand.

### Editing and publishing

- The web editor is «Apariencia de la tienda» in web settings (`settings/store-appearance`, plain and language-prefixed), in the panel menu. The old address `settings/checkout-appearance`, plain or language-prefixed, answers 308 to the new one with the same prefix and query. Reason: bookmarks and habits keep working. The mobile app has its own screen ([Mobile editor](#mobile-editor)). Any user who can manage the company's settings can edit it; no new role exists.
- Sections: **Logo**, **Tema**, **Restablecer apariencia** and the **Publicar catálogo** card, where the seller chooses the catalog link and publishes ([Public catalog · Publicar catálogo card](public-catalog.md#publicar-catálogo-card)). The card is drawn as its own surface, apart from Logo and Tema, and is reached at `#catalog-publication`. **Tema** is a single-choice list, «Temas de la tienda», of the five themes in the fixed order Clásico, Boutique, Antojo, Suave, Noche; each option shows a static sample painted with the theme's real values (page background, a card, the primary button and the thumbnail shape), its name, a one-line description and a check mark when selected. One theme is always selected; choosing the selected one again changes nothing. On the phone the editor has **Editar** and **Vista previa** tabs, with the publication card in **Editar**; touch targets are at least 44 px.
- The editor itself keeps the Yoyos identity; the selected theme is visible only in the samples and the preview.
- Logo and theme changes stay in a session draft and are previewed live with the «Cambios sin guardar» badge; nothing is published until **Guardar cambios**, which publishes logo and theme together as one unit («Apariencia actualizada»). The catalog link and the publication switch are outside the draft: the link saves with its own **Guardar link** and the switch at once. «Apariencia actualizada» never means the link was saved.
- **Descartar cambios** restores the published appearance. **Restablecer apariencia** prepares Clásico without logo in the draft, still requires saving, and never touches the publication. Leaving with unsaved logo or theme changes, or with an unsaved catalog link ([Public catalog · Saving, changing and failures](public-catalog.md#saving-changing-and-failures)), including reloading or closing the tab, asks «Tienes cambios sin guardar» with «Seguir editando» or «Descartar y salir». The description says what is pending: only logo or theme, «Si sales ahora, perderás los cambios que no publicaste.»; only the link, «Si sales ahora, no se guardará el link que escribiste.»; both, «Si sales ahora, perderás los cambios que no publicaste y el link que escribiste.». On reload or tab close the browser shows its own generic dialog. The publication switch never counts as an unsaved change, and an unsaved link never shows the badge or enables **Guardar cambios** or **Descartar**.
- **Independent loading:** the appearance (logo, theme, preview) and the publication card load and fail separately. An appearance read failure replaces Logo, Tema and preview with «No se pudo cargar la apariencia» and **Reintentar**, hides **Guardar cambios**, **Descartar** and **Restablecer apariencia**, and leaves the card working. **Reintentar** re-reads both parts without reloading the page and keeps the draft. A failure of the card's link check, save or re-read stays inside the card and never clears the draft or the typed link. Reason: the card is the only place to hide the catalog.
- **Unknown stored theme:** the editor shows exactly what buyers see, Clásico selected and no logo, with «No pudimos usar tu apariencia guardada. Tus clientes ven tu tienda con el tema Clásico y sin logo. Elige tu tema y tu logo y guarda.». It is never a load error. That starting point is not a draft: no badge, no **Descartar**, no **Restablecer apariencia**, and leaving untouched asks nothing; **Guardar cambios** is enabled, so saving as is stores Clásico without logo. After a change the usual draft applies, and **Descartar** returns to Clásico without logo with the notice still shown. The notice disappears after the first successful save. Reason: the editor shows only what buyers see, and a rare corrupt record must not nag the seller on every visit.
- **Other unusable stored data** (anything other than an unknown theme) stays a load error of Logo, Tema and preview, with the publication card working; buyers see Clásico without logo. It is an accepted limitation: very rare, since the database protects the logo reference, and the seller cannot change logo or theme until the data is fixed by hand.
- **Stored logo that cannot be shown:** if the stored logo's image cannot be resolved, the editor (web and mobile) loads with the stored theme and «Sin logo» with **Subir logo** and no **Quitar logo**; buyers see the stored theme without logo. A save that does not touch the logo keeps the stored logo; uploading a new one replaces it. Reason: a valid theme is not dropped over an image URL, and no client erases the logo.
- A save rejected for an unknown theme shows «Revisa el tema e inténtalo de nuevo.»; one rejected for an invalid logo shows «No pudimos usar ese logo. Súbelo de nuevo.». The draft is kept in both cases.
- A save that fails or gets no response shows «No pudimos guardar la apariencia. Conservamos tu borrador.» with **Reintentar**. The draft is kept, also when the editor's reload after the lost save fails too; the published appearance is whatever the server last completed. Repeating the save publishes the same logo and theme again, so it cannot duplicate or mix anything. A failed logo upload offers its own **Reintentar** and does not touch the theme.
- The web editor checks the byte limit before uploading; a server rejection for the logo's dimensions shows «El logo es demasiado grande. Usa una imagen de hasta 8000 px por lado.». The limits come from `imageUploadLimits` in `shared/contracts/images.ts`, read by the server, the web editor and the mobile app. Reason: no client checks a different number than the server.
- The last completed save wins, also between web and mobile; there is no versioning or optimistic lock. Reason: it is a complete visual configuration with nothing to merge.
- Uploading a logo does not publish it; a logo uploaded and never saved stays an orphan image. The logo must be a public image of the same company (enforced by a composite foreign key) and is visible to buyers.
- The company ID always comes from the session, never from the request body. A request that sends a brand color, a background or any unknown key is rejected.
- Code and logs use the name «store appearance»; the stored data keeps its table `CompanyCheckoutAppearance` and enum `CheckoutTheme`. Reason: one name per concept in code at no database cost (rejected: renaming the table, enum and RLS policy, a migration with an exclusive lock for no visible gain).

### Preview

- An iframe renders the real catalog and checkout components with the draft logo and theme. A selector **Catálogo** | **Checkout** (accessible name «Vista previa», touch targets of at least 44 px) chooses the surface; it opens on **Catálogo** every time the editor loads, because the catalog is what the buyer sees first. Switching keeps the draft and the device choice, and does not reload the iframe.
- One label names the active view: the theme and the origin of the data, «Tema Boutique · Tus productos» or «Tema Boutique · Datos de ejemplo». The checkout view always uses sample data and shows the payment step (never the confirmed block or the closing screen); its payment state shows «Monto a pagar» and the summary ends in «Total del pedido».
- The phone/desktop switch applies to both views; the review/payment switch exists only in **Checkout**, which has no closing-screen state. There is no light/dark switch: each theme's mode is fixed, so the preview shows it as the buyer sees it. Reason for the iframe: it has its own viewport, so the real breakpoints apply without rewriting the pages.
- **Catálogo** view: a short catalog with header (logo plate and store name), search field, the first three products in the catalog's own order (only products the catalog would show), each card with its product's primary photo, and the floating cart button.
  - The products are read once per editor visit, also while the catalog is hidden: it previews the look, not the publication. Saves, publication changes and **Reintentar** never re-read them.
  - While they load, the view shows the header and three empty card placeholders in the draft theme with «Cargando productos»; it never shows samples first and swaps them for real ones.
  - A company with one or two visible products sees only those; one with none, or whose products fail to load, sees three sample products. Real and sample products are never mixed. Reason: padding with samples would show the seller a store that is not theirs. A product-load failure never blocks the editor.
  - The cart button looks like the real one with one unit, «Carrito» with the badge «1» and no amount, standing for the first product shown that is not «Agotado»; if every product shown is sold out, it shows no units.
- **Checkout** view: sample order, buyer and amounts. The sample order has one product with a sample photo and one without, so both the thumbnail and the marker are visible. The payment state shows the company's offered payment methods ([Payment methods](#payment-methods)), or labeled examples if it has none or they cannot be read.
- The preview does not read the stored appearance: it stays blank until the editor sends the first draft, so an unknown or unusable stored appearance never breaks it. Only a failed company-name read fails it.
- It is inert: it never navigates, searches, adds to a cart, sends requests, creates orders or registers payments. The catalog view's search field, cards and cart button are out of the keyboard focus order and hidden from screen readers, which announce only the view's label. The iframe is sandboxed without form submission and messages are validated by origin and schema.

### Mobile editor

- Settings → «Apariencia de la tienda» («Logo, tema, link y publicación de tu catálogo»), between the delivery row and Catálogo. It is a single scrolling editor with no tabs; opened from Catálogo (`focus=catalog`) it scrolls to the **Publicar catálogo** card without opening the keyboard. It keeps the app's own look; the selected theme shows only in the samples.
- **Logo** on its white plate, or «Sin logo» (announced as «Logo de tu tienda» when present); **Subir logo** or **Cambiar** from the gallery or the camera; **Quitar logo**; «Subiendo logo…» while uploading.
- **Tema**: the five themes in the fixed order, with static samples painted with each theme's colors, rounding, button shape and thumbnail shape in the phone's system font, name, description and check mark; announced as the single-choice group «Temas de la tienda». The app bundles no theme fonts. Reason: no extra weight in the app for a sample.
- **Publicar catálogo**: the same card as on web, with the catalog link (saved with **Guardar link**) and the switch (saved at once). While the link field has focus, the field, its status line and **Guardar link** stay visible above the keyboard and the save bar.
- **Save bar**: only while logo or theme differ from the published ones, fixed at the bottom above the tab bar, with «Cambios sin guardar», **Descartar** and **Guardar cambios**. Uploading a logo with no other change shows no bar until the upload finishes. While a logo uploads, **Guardar cambios** is disabled; while saving, it reads «Guardando…» and the bar buttons, logo actions and theme list are disabled, but the publication switch stays usable. A successful save hides the bar and shows «Apariencia actualizada» under the screen description, announced politely; a failed save keeps the bar with the save error and **Reintentar**.
- Leaving the settings stack with unsaved logo or theme changes or an unsaved catalog link asks «Tienes cambios sin guardar» with **Seguir editando** / **Descartar y salir** and the same three descriptions as on web; switching tabs does not ask and keeps the draft. Same pattern as delivery settings.
- Loading, the unknown stored theme (the save bar shows only **Guardar cambios**) and an unresolved stored logo behave as on web.
- No live preview and no **Restablecer apariencia**: the seller gets the same result by choosing Clásico and removing the logo, and sees the result in **Ver catálogo** once the catalog is published. Accepted gap until phone-only sellers ask to see the theme before publishing.
- **Logo files.** The logo is never processed like a product photo, which is re-encoded as JPEG and would put a solid box behind a transparent logo on every buyer page.
  - PNG, JPG and WEBP are uploaded byte for byte with their own type: never re-encoded, resized or flattened, so a transparent logo reaches buyers as it would from web. The picker keeps the original file (no editing).
  - HEIC/HEIF gallery photos and camera photos are converted to JPG, scaled to at most 1024 px on the longest side and reduced in quality until they weigh 10 MB or less. Reason: the logo shows at header size on every buyer page, and a full-size camera JPG would make every buyer download several megabytes. **Reintentar** after a failed conversion or upload converts the chosen photo again.
  - Before uploading: any other format shows «Usa una imagen PNG, JPG o WEBP.»; a PNG, JPG or WEBP over 10 MB shows «El logo debe pesar hasta 10 MB.»; one over 8000 px per side or 24 megapixels shows «El logo es demasiado grande. Usa una imagen de hasta 8000 px por lado.». None is shrunk, so the logo is never altered. The server still validates by content.
  - Hint: «PNG, JPG o WEBP hasta 10 MB, o una foto de tu galería o cámara. Tus clientes verán este logo en tu catálogo y en tu checkout.»

### API

The mobile app reads and saves the appearance through `GET` and `PUT /api/store-appearance` (bearer token or session with an active company; the company and user come only from access). Request, response and error codes are defined in `shared/contracts/store-appearance.ts`; responses are `no-store`. The web editor uses its own loader and action instead.

- `GET` answers the readable appearance (theme and logo `{ id, url }`) or `unknown_theme`; Clásico without logo for a company that never saved one. Other unusable stored data answers `503 INVALID_STORED_DATA`.
- `PUT` takes `{ theme, logoImageId }` and answers the saved appearance, which mobile uses as its new baseline without reading again. An unknown theme, an unknown key or a bad id answers `400 INVALID_STORE_APPEARANCE`; malformed JSON `400 INVALID_INPUT`; a logo that is missing or of another company `422 INVALID_IMAGE`; a non-JSON body `415`. Rejections never change the published appearance.
- A logo whose URL cannot be built comes back as `url: null` with its id, so a theme-only save keeps it; a save that committed is never reported as failed because the URL could not be built afterwards.
- The logo is uploaded with the existing `POST /api/images`; the catalog link and publication use the catalog settings API ([Public catalog · Data and API](public-catalog.md#data-and-api)). Saving the appearance, the link and the publication never change each other.

### Buyer view

- The theme applies to the whole checkout in every state: pending, delivery choice, the payment step, the closing screen, paid, cancelled, and the total-changed and rate-error notices. The closing card, summary label and amount rows are themed like the rest. The catalog's themed screens are listed in [Public catalog · Theme](public-catalog.md#theme).
- The appearance is read only after the order access is authorized; «Enlace no disponible» keeps the unbranded Yoyos look and follows the buyer's system preference.
- Opening or reloading a link shows the latest published theme and logo, including links shared before and historical orders; no per-order or per-cart copy is kept.
- Without a saved appearance, or if reading it fails, the checkout uses Clásico without logo and the order can still be confirmed and paid. Reason: a visual failure must never block a sale.
- The theme styles are scoped to the themed subtree of the checkout or catalog (and the page background behind it) and never change the private panel. The catalog's cart sheet renders inside that subtree so it keeps the theme. The active theme's styles are generated in the browser from `shared/store-themes.ts`, the same mechanism the editor preview needs for drafts; it adds a few KB to the buyer bundle, accepted to keep one mechanism for every surface.

## Observability

Logging follows [logging conventions](logging.md).

- The full checkout URL is a credential: raw URLs are never logged. Routes are normalized to `/checkout/:orderId` and `/api/orders/:orderId/checkout-link`; New Relic obfuscates UUIDs in URLs and excludes the `orderId` attribute (`apps/core/newrelic.cjs`).
- Buyer data, request bodies, payment data and amounts are never logged.
- `http_request_completed` carries a closed `operation` (`enable_checkout` for the seller's link read, `get_checkout`, `confirm_checkout`) and `outcome`; the link read's outcome is `loaded`, `unavailable` (no subdomain) or `technical_failure`. Expected rejections (invalid input, total changed, cancelled, already confirmed, unavailable) do not emit `warn` or `error`. A request for the checkout on the app host is logged as `unavailable`.
- A checkout delivery projection that fails its contract logs `checkout_delivery_options_invalid` (error) with the path of the first issue (`field`) and its Zod code (`issueCode`), and the page shows its load error.
- Buyer quotations log `buyer_quotation_created` ([Delivery · Observability](delivery.md#observability)).
- `order_checkout_confirmed` is emitted only for the first confirmation and only after the transaction commits. Reason: a rolled-back write must not look like a success. Enabling is part of creating the order, so it has no event of its own.
- A failed read of the subdomain while building the web order link logs `order_checkout_link_unavailable` (error) and the card offers **Reintentar**. A failed lookup of the brand host's company for a buyer API logs `buyer_api_owner_failed` and answers `503`.
- Each technical failure has a single log owner; upper layers propagate the `Result` without logging it again.
- A save of the store appearance (web or mobile) logs `store_appearance_saved` with the theme, whether there is a logo, whether the appearance is the default and, with a logo, its image id. Joined with `image_uploaded` (images module: type, bytes and dimensions), it shows how heavy the logos buyers download are.
- Checkout and catalog requests are tagged with `storeAppearance: default | custom | fallback` and `storeTheme` (`classic` … `noche`). In the checkout, a failed appearance read logs `order_store_appearance_failed`; in the catalog, `unable_to_read_catalog` with `operation: read_appearance`. Both fall back to Clásico without logo.
- The store appearance repository logs `invalid_stored_store_appearance` (`errorCode` `UNKNOWN_STORED_THEME` or `INVALID_STORED_DATA`, with field names only), `unable_to_load_store_appearance` and `unable_to_save_store_appearance`. A logo URL that cannot be built for the seller read or the save logs `store_logo_url_unavailable` (warn); the buyer read does not log it, so a storage outage adds no warning per buyer request.
- The mobile API logs `store_appearance_response_invalid` when its own response fails the contract and `store_appearance_request_failed` for an unexpected failure. Its request operations are `get_store_appearance` and `save_store_appearance`; a `415` is answered before any operation is bound.
- Editor request operations: `get_store_appearance`, `save_store_appearance`, `set_catalog_publication`, `get_store_preview` and `get_catalog_preview_cards`; the link group adds `get_catalog_settings`, `check_catalog_subdomain` and `save_catalog_subdomain`. A failed preview-card read logs `unable_to_read_catalog` (`read_preview_store` or `read_preview_cards`).
- A failed photo lookup for the checkout logs `order_checkout_photos_unavailable` (orders, with the variant count) and, when the variant query itself fails, `unable_to_read_variant_photos` (products infrastructure); photos whose image cannot be resolved are reported by the existing `product_list_images_unavailable`. The checkout still loads with markers. Photo and logo URLs are never logged.
